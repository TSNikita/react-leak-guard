# Глава 3: Архитектура LeakGuard Engine

## 3.1. Введение

В предыдущих главах мы показали, что утечки памяти в React возникают из-за того, что асинхронные операции (fetch, timers, event listeners) и обновления состояния (`setState`) продолжают выполняться после того, как компонент был размонтирован.

Существующие решения требуют от разработчика ручного написания кода очистки (cleanup) или используют статический анализ, который не видит runtime-ошибок.

**react-leak-guard** решает эту проблему иначе. Вместо того чтобы полагаться на дисциплину разработчика, библиотека перехватывает жизненный цикл компонентов и асинхронные операции на уровне runtime, автоматически предотвращая утечки.

В этой главе мы разберём архитектуру ядра библиотеки — **LeakGuard Engine**.

---

## 3.2. Ключевые компоненты архитектуры

Архитектура LeakGuard Engine состоит из четырёх основных модулей, которые работают в тесной связке:

1. **Lifecycle Registry (Реестр жизненного цикла)**
2. **StateUpdateProxy (Прокси обновления состояния)**
3. **AutoCleanup Engine (Движок автоматической очистки)**
4. **LeakBuffer (Буфер диагностики утечек)**

Разберём каждый из них подробно.

---

### 3.2.1. Lifecycle Registry (Реестр жизненного цикла)

**Проблема:** Чтобы знать, когда компонент размонтирован, нужно отслеживать его состояние. Если хранить ссылки на компоненты в обычном `Map` или массиве, мы сами создадим утечку памяти, так как реестр будет удерживать компоненты в памяти даже после их уничтожения.

**Решение:** Мы используем `WeakMap`.

```typescript
// Упрощённый пример структуры данных
const componentRegistry = new WeakMap<object, ComponentState>();
```

**Почему WeakMap?**
- `WeakMap` хранит слабые ссылки (weak references) на объекты-ключи (в нашем случае — экземпляры React-компонентов).
- Если компонент размонтирован и на него больше нет внешних ссылок, Garbage Collector (GC) автоматически удалит его из памяти, а `WeakMap` сам очистит соответствующую запись.
- Это гарантирует нулевой оверхед по памяти (Zero Memory Overhead) для самого реестра.

**Что хранится в реестре:**
Для каждого зарегистрированного компонента мы храним:
- `isMounted: boolean` — флаг монтирования.
- `trackedOperations: Set<Operation>` — список активных асинхронных операций.
- `leakCount: number` — счётчик заблокированных утечек.

---

### 3.2.2. StateUpdateProxy (Прокси обновления состояния)

**Проблема:** Самая частая и опасная утечка в React — вызов `setState` (или `dispatch` из `useReducer`) на размонтированном компоненте. Это приводит к предупреждениям в консоли, гонкам состояний (race conditions) и потере данных.

**Решение:** Мы оборачиваем оригинальный `setState` в прокси-функцию.

```typescript
function createSafeSetter(component, originalSetter, componentName) {
  return function safeSetter(newValue) {
    if (!isMounted(component)) {
      // 1. Блокируем обновление
      // 2. Записываем факт утечки в LeakBuffer
      recordLeak(componentName, 'setState');
      return; 
    }
    // Если компонент жив — передаём управление оригинальному setter
    return originalSetter(newValue);
  };
}
```

**Как это работает на практике:**
Разработчик использует наш хук `useSafeState` вместо `useState`. Под капотом хук возвращает не обычный `setState`, а `safeSetter`.
- Пока компонент смонтирован, `safeSetter` работает идентично обычному `setState` (оверхед близок к нулю).
- Как только компонент размонтирован, `safeSetter` "умирает" вместе с ним, блокируя любые попытки обновления.

---

### 3.2.3. AutoCleanup Engine (Движок автоматической очистки)

**Проблема:** Разработчики часто забывают возвращать функцию очистки (cleanup function) из `useEffect`.

**Решение:** Мы предоставляем API для "трекинга" операций. Когда разработчик регистрирует операцию (например, таймер или подписку) в нашем реестре, движок автоматически вызывает её очистку при размонтировании компонента.

```typescript
// Пример использования API
const timerId = setInterval(() => {...}, 1000);
engine.trackOperation(component, {
  type: 'timer',
  cleanup: () => clearInterval(timerId),
  source: 'MyComponent'
});
```

**Механизм работы:**
1. При вызове `trackOperation` ссылка на функцию `cleanup` сохраняется в `WeakMap` рядом с компонентом.
2. При вызове `unregister(component)` (который происходит автоматически при unmount через наш хук `useLeakGuard`), движок проходит по всем сохранённым операциям и принудительно вызывает их функции `cleanup`.
3. Это происходит гарантированно, даже если разработчик забыл написать `return () => ...` в `useEffect`.

---

### 3.2.4. LeakBuffer (Буфер диагностики утечек)

**Проблема:** В production-среде разработчик "слеп". Он не знает, что в приложении пользователей происходят утечки, пока не получит жалобу на "тормоза" или краш вкладки.

**Решение:** `LeakBuffer` — это лёгкий буфер в памяти, который агрегирует статистику заблокированных утечек.

**Что он записывает:**
- Имя компонента, в котором произошла утечка.
- Тип операции (`setState`, `fetch`, `timer`, `eventListener`).
- Временную метку (timestamp).
- Стек вызовов (только в режиме разработки).

**Как это используется:**
- **В Development:** Буфер выводит подробные предупреждения в консоль браузера с указанием точного места в коде.
- **В Production:** Буфер хранит агрегированные данные (например, `{ "UserDashboard": 5, "ChatWidget": 12 }`). Эти данные могут быть отправлены в систему мониторинга (Sentry, Datadog) через callback-функцию, позволяя командам находить и чинить утечки в реальном продакшене.

## 3.3. Поток данных (Data Flow)

Чтобы понять, как все компоненты работают вместе, рассмотрим полный жизненный цикл компонента, защищённого `react-leak-guard`.

### Фаза 1: Монтирование (Mount)
1. Компонент рендерится.
2. Вызывается хук `useLeakGuard()`.
3. Экземпляр компонента регистрируется в `Lifecycle Registry` (WeakMap). Статус: `isMounted = true`.
4. Хуки `useSafeState` и `useSafeReducer` инициализируют прокси-функции.

### Фаза 2: Runtime (Работа компонента)
1. Компонент делает запрос к API или запускает таймер.
2. Разработчик (или наш автоматический перехватчик) регистрирует операцию в `AutoCleanup Engine`.
3. Если происходит вызов `setState`, `StateUpdateProxy` проверяет `isMounted`. Если `true` — обновление проходит.

### Фаза 3: Размонтирование (Unmount)
1. Пользователь уходит со страницы. React вызывает cleanup для `useLeakGuard()`.
2. Статус компонента меняется на `isMounted = false`.
3. `AutoCleanup Engine` итерируется по всем зарегистрированным операциям компонента и вызывает их `cleanup` функции.
4. Если после этого какой-то внешний код (например, завершившийся Promise) попытается вызвать `setState`, `StateUpdateProxy` перехватит вызов, заблокирует его и запишет факт утечки в `LeakBuffer`.
5. `WeakMap` теряет ссылку на компонент. Garbage Collector удаляет его из памяти. Утечка предотвращена.

## 3.4. Два режима работы

Архитектура LeakGuard Engine спроектирована так, чтобы работать по-разному в зависимости от окружения. Это критически важно для производительности.

### Режим Development (Разработка)
- **Цель:** Максимальная диагностика и помощь разработчику.
- **Поведение:**
    - Выводит подробные `console.warn` при каждой заблокированной утечке.
    - Собирает полные стеки вызовов (stack traces).
    - Включает строгие проверки типов.
- **Оверхед:** Незначительный (только на запись логов), приемлемый для локальной разработки.

### Режим Production (Продакшен)
- **Цель:** Нулевой оверхед и защита пользователей.
- **Поведение:**
    - Молча блокирует `setState` и вызывает `cleanup`. Никаких `console.warn`.
    - Не собирает стеки вызовов (экономит память и CPU).
    - Только агрегирует счётчики в `LeakBuffer` (опционально, для отправки в телеметрию).
- **Оверхед:** Близок к нулю. Проверка флага `isMounted` — это одна операция чтения из `WeakMap`, которая занимает наносекунды.

---

## 3.5. Ключевые инновации (Патентная чистота)

Архитектура LeakGuard Engine обладает рядом свойств, которые отличают её от существующих аналогов (React Query, ahooks, Memlab):

1. **Неинвазивность (Non-invasive):** Библиотека не требует переписывания существующего кода на специальные хуки (как `useQuery`). Она может работать как "обёртка" над стандартным `useState` и `useEffect`.
2. **Гарантированная очистка (Guaranteed Cleanup):** В отличие от ESLint или React Strict Mode, которые только предупреждают о проблеме, наш `AutoCleanup Engine` физически выполняет очистку ресурсов, даже если разработчик забыл написать `return () => ...`.
3. **Runtime-перехват (Runtime Interception):** Мы блокируем утечки в момент их возникновения, а не постфактум (как Memlab или Chrome DevTools).
4. **Безопасность памяти (Memory Safety):** Использование `WeakMap` гарантирует, что сама библиотека никогда не станет причиной утечки памяти, удерживая ссылки на уничтоженные компоненты.

Архитектура LeakGuard Engine представляет собой комплексную систему защиты памяти, которая работает на уровне runtime. Она сочетает в себе преимущества автоматического управления ресурсами (как в языках с RAII, например, C++ или Rust) и гибкость JavaScript.
