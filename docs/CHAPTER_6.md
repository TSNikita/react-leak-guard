## 6.2. Интеграция в существующий проект

Интеграция `react-leak-guard` спроектирована так, чтобы быть максимально простой и не требовать рефакторинга всего приложения.

### Шаг 1: Установка
```bash
npm install react-leak-guard
# или
yarn add react-leak-guard
```

### Шаг 2: Инициализация (Опционально)
Если вы хотите собирать телеметрию об утечках в production, инициализируйте движок в корне приложения:

```typescript
import { initLeakGuard } from 'react-leak-guard';

initLeakGuard({
  mode: process.env.NODE_ENV === 'production' ? 'production' : 'development',
  onLeakDetected: (report) => {
    // Отправка отчёта в Sentry, Datadog или ваш логгер
    console.error('Memory leak detected:', report);
  }
});
```

### Шаг 3: Использование в компонентах
Замените стандартный `useState` на `useSafeState` в компонентах, где есть асинхронная логика:

```typescript
// Было
const [data, setData] = useState(null);

// Стало
const componentRef = useLeakGuard('MyComponent');
const [data, setData] = useSafeState(componentRef, 'MyComponent', null);
```

## 6.3. Стратегия миграции

Внедрять библиотеку во всё приложение сразу не рекомендуется. Мы предлагаем **поэтапную стратегию миграции**:

### Этап 1: Критические зоны (Hotspots)
Найдите компоненты, которые чаще всего вызывают утечки (обычно это дашборды, чаты, карты, графики). Внедрите `useSafeState` и `useLeakGuard` только в них. Это даст 80% пользы при 20% усилий.

### Этап 2: Асинхронные хуки
Если вы используете кастомные хуки для работы с API (например, `useFetch`), оберните их внутренние `setState` в `createSafeSetter`. Это защитит все компоненты, использующие этот хук, без изменения их кода.

### Этап 3: Глобальная защита (Future)
В версии 1.0 мы планируем выпустить Babel-плагин, который будет автоматически оборачивать все `useState` и `useEffect` в безопасные аналоги на этапе компиляции. Это позволит включить защиту во всём приложении с помощью одной строки в конфиге, без изменения исходного кода.

## 6.4. Лучшие практики (Best Practices)

Хотя `react-leak-guard` выступает как "последняя линия обороны", мы рекомендуем соблюдать следующие практики:

1. **Не удаляйте ручной cleanup, если он уже есть.** Если вы написали `return () => clearInterval(id)` в `useEffect`, оставьте его. LeakGuard не заменяет хороший код, он страхует от ошибок.
2. **Используйте осмысленные имена компонентов.** Передавайте понятные имена в `useLeakGuard('UserProfile')`. Это критически важно для диагностики утечек в production через LeakBuffer.
3. **Мониторьте LeakBuffer в production.** Настройте алерты в Sentry или Datadog на резкий рост счётчика утечек. Это поможет находить регрессии до того, как пользователи начнут жаловаться на тормоза.

## 6.5. Roadmap: Что дальше? (Версия 1.0 и выше)

Разработка `react-leak-guard` только начинается. Вот наш план развития на ближайшие 6 месяцев:

### v0.3.0 (Текущий этап)
- ✅ Базовая защита `setState` и `useReducer`.
- ✅ Ручной трекинг операций (`trackOperation`).
- ✅ Сбор телеметрии через `LeakBuffer`.

- 🔄 Визуализация утечек в виде графа зависимостей в React DevTools.

- 🚀 Интеграция с ESLint: Кастомное правило, которое предупреждает об использовании нативного `useState` вместо `useSafeState`.
- 🚀 Стабильный публичный API и гарантия обратной совместимости (SemVer).

## 6.6. Заключение

Утечки памяти в React — это системная проблема, порождённая самой природой JavaScript (сборка мусора, замыкания, асинхронность) и императивным API браузера (таймеры, события). Долгое время индустрия пыталась решать её вручную, полагаясь на внимательность разработчика.

**react-leak-guard** меняет парадигму. Мы переносим ответственность за управление памятью с человека на машину, создавая слой автоматической безопасности, который работает в runtime, не требуя переписывания кода и не влияя на производительность.

Эта методичка описывает не просто библиотеку, а **новый стандарт безопасной разработки** на React. Мы приглашаем сообщество к тестированию, обсуждению и совместному развитию этого проекта.
